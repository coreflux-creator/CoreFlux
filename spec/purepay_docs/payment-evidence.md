# Core payment result evidence

## Isolated financial preview routing

Financial reads and signed callbacks use the separate `purepay_connections` setup; a reviewed staffing binding alone does not configure them. The optional private PHP constant or environment setting `COREFLUX_PUREPAY_FINANCIAL_PREVIEW_API_BASE` admits only `https://pure-pay-support.preview.emergentagent.com/api/v1` and only when `COREFLUX_STAGING === true`. The constant takes precedence on hosts where `putenv()` is disabled. Before enabling this application-wide setting, verify the isolated installation and all existing financial connections; changing the origin invalidates prior payment connection fingerprints.

This observation mode blocks outbound financial POST/PUT/PATCH/DELETE requests before transmission, including payouts and bill/vendor creation. Connection storage and fingerprints are restricted to the approved simulation tenant 999; connection reads exclude other tenants and any saved write-enabled connection. Existing staffing writes retain their explicit, separately reviewed destination and operation controls. Signed inbound callbacks still require their own tenant connection, stored secret and valid payment evidence. Enabling routing alone does not establish a provider organization, subscribe an endpoint, authorize payment execution or prove callback delivery.

The `pilot_payment_preview` deployment action requires the exact installed adapter/service sources, original reviewed private-config hash, simulation/instance identity, Meridian staffing binding and the existing operator's authority. It locks and checks the entire financial connection/link/event set is empty, retains an owner-preserving private backup, then atomically adds the preview constant. A fresh CLI check and temporary token-protected PHP-FPM probe verify the read-only route. This action creates no API key, webhook secret, subscription, payment link or financial record. An interrupted configuration switch retains recovery evidence and can resume only with the original or exact prepared configuration and an empty financial setup.

Core's vendor-payment rail reserves one USD obligation for each durable attempt. A provider bill ID and terminal status alone cannot settle or release that reservation. A $40 payment against its bill must not settle a $125 Core payment.

The outgoing wallet request includes the exact amount from that durable Core claim. It must not delegate amount selection to a PurePay payment plan or the bill's current balance. PurePay still rejects an explicit amount above its open balance before creating a payment. This prevents amount drift; it does not establish a shared reservation against another system paying the underlying obligation through a different record or rail.

The Core consumer requires the following evidence from an authenticated payment-detail read or verified signed callback. Complete bill-specific history only locates a payment; Core then reads its full detail so the compact history projection cannot conceal allocation semantics:

| Field | Meaning and validation |
| --- | --- |
| `id` or `payment_id` | Actual provider payment ID; both must agree when present. |
| `bill_id` or `payable_id` | Exactly the bill bound to the original Core attempt; both must agree when present. |
| `amount` | Gross amount for the one directly linked bill, matching Core's entire reserved amount to the cent. Decimal dollars, at most two decimal places; no rounding. |
| `currency` | Explicit `USD`. Missing currency is unknown, including on historical records. |
| `status` or `pay_status` | Explicit recognized payment state; multiple aliases must agree. A callback must also agree with its event type. |

Provider `gross_cents`, when present, must be an integer equal to the reserved cents. PurePay's stored `amount_cents` means the **net transfer**, unlike Core's request field of the same name. It requires explicit matching `net_cents`; those values must be positive integer cents no greater than the gross amount. They never substitute for the gross bill obligation. Ledger-only QuickBooks receipts and Mercury request acknowledgements do not prove delivery.

A QuickBooks bookkeeping reference can coexist with an actual Moov result: `moov_transfer_id` must be a valid identity, and `moov_status` must agree with the payment state (`completed` for settled, `failed`, `reversed` for returned, or `canceled`/`cancelled`). Missing or contradictory rail evidence is held. Explicit QuickBooks-only and Mercury methods remain unconfirmed. These checks also apply when rail fields are supplied without a bookkeeping reference.

The callback receiver accepts distinct settled, failed, returned and cancelled events. A return, cancellation or failure following settlement is held for reconciliation instead of reversing accounting automatically. An event ID is bound to its original signed bytes; changed-content reuse is rejected. An unmatched or review-held callback returns a retryable response after recording the reason; an already processed identical event is acknowledged without processing again.

The held PurePay preview also separates receipt of an incoming Moov event from completion. A durable event and transfer claim serialize provider redelivery; guarded status writes can resume after interruption. Before each unfinished phase, company ownership, linked records and expected state are checked again. An interrupted financial helper stays in `needs_review` instead of being blindly repeated. Legacy receipt-only rows do not prove completion. A bounded platform-admin read lists unfinished metadata without exposing payloads or adding a force-retry action. Recovery currently depends on provider redelivery; live delivery and operational reconciliation remain acceptance requirements.

PurePay's existing `allocated` response field describes an adjustment or overpayment, not an allocation of payment money to a bill. A nonzero adjustment, partial result, or multi-bill allocation structure requires review. The current consumer does not sum partial payments or apply a multi-bill payment total to one Core reservation. Supporting those cases requires a separate explicit allocation contract.

Core persists a versioned receipt after validating the result. Retries and the final AP clearance/cancellation checks require that receipt to match the saved payment, bill, amount, and status. An unreadable, missing, ambiguous, or conflicting current result adds a review hold while preserving the prior receipt and reservation. A fresh consistent result can resolve the hold. Status-only historical rows require reconciliation; they are not automatically backfilled.

Each provider payment ID has one receipt owner per Core company. Migration 175 enforces this at the database boundary with case-sensitive identity, independent of the credential fingerprint. A rotated credential cannot make an already recorded payment available for a second Core attempt. Historical duplicates stop migration without changing their evidence; both attempts fail replay and AP clearance/release checks until reviewed. Migration 176 adds a reviewed, permanent, exclusive provider-organization claim. Neither receipt ownership nor organization binding reserves the supplier's underlying obligation across different provider bills or payment rails.

## Reviewed original bill identity

Migration 177 and `api/purepay_bills.php` add an explicit comparison from a Core AP bill to an existing PurePay bill. The bill detail page displays stable bill/vendor IDs, the Core legal entity, provider organization, invoice number, dates, original total, currency and vendor remit identity. Only an authenticated operator with both AP view and financial-integration management permissions can review or confirm a link. Provider access is GET-only, outside database transactions, and requires the separately confirmed financial company. Bank and tax values are excluded from the review snapshot.

Confirmation re-reads provider evidence, compares the displayed review hash, then locks and rechecks the local bill, vendor, entity and company binding. The original bill must already be approved, partly paid or paid. Invoice number, dates, total, explicit USD currency, vendor name and remit email must agree. Missing historical provider currency remains unknown and blocks the link; it is never inferred from the UI or a wallet. A unique origin/organization/provider-bill key prevents two Core bills from claiming the same provider bill. The saved Core bill, vendor and legal entity cannot be retargeted. Key rotation retains these identities but invalidates current review until the operator confirms fresh evidence. Each distinct review and its mandatory audit are committed atomically; an identical replay retains the original review.

This is an identity link, not a reservation or execution contract. It does not create provider bills, reconcile balances, adopt historical payment receipts, allocate payments, change existing vendor mappings, or alter the current payment dispatch path. Its summary explicitly distinguishes saved identity from a fresh provider read. Dispatch must still be connected to this canonical bill model, with shared provider reservations and an explicit partial/multi-bill allocation contract. These remaining steps are required before the link can authorize payment execution.

## Provider compatibility gate

PurePay source `20b21f9bf0939a9479adfb5329d3edc8fe591e46` is installed in the held `pure-pay-support` preview. New wallet records store explicit USD from the execution contract and exact gross cents. Invalid money or incompatible bill currency is rejected before storage. Terminal callbacks re-read the exact tenant/bill/payment, retain amount and currency, and require agreeing rail evidence when present. Cached results cannot override missing or conflicting current records.

The provider uses the existing payment event log and a bounded cyclic scan of saved payment records to recover missed enqueue attempts and missing log writes, durable company/endpoint/event identities, leased batches and retry backoff. The cyclic scan revisits older updated rows and newly subscribed endpoints without changing payment records or refreshing payment rails. It cannot recover a rail result that was never persisted. Each delivery rechecks the current payment and endpoint. Retries retain the same signed body and event ID with a fresh timestamp; stale unsent results are superseded. Settled, failed, returned and cancelled are separate subscriptions. Existing endpoints were not automatically resubscribed.

The installed sources passed 88 isolated full-application checks without source overlays, real database access or network calls. The suite exercises the actual emitter and signed HTTP delivery using in-memory Mongo and mock HTTP, plus review-mode startup. This proves those bounded contracts, not a live payout or Thunderhawk callback. The preview worker remains disabled. Core runtime `8fd81fc550232c2582dd7bd645e65f4d42458053` passed all nine CI jobs, including 87 money-evidence and 278 MariaDB delivery checks, and isolated staging acceptance. Evidence is in `deploy/purepay-payment-recovery-preview-20261025.json` and the earlier `deploy/purepay-payment-callbacks-staging-20261025.json`; full provider receipts are saved with its source and under `/app/audit/core-payment-recovery-2026-10-25`.

Live compatibility remains unproven until provider-to-Core delivery/replay and the intended endpoint subscriptions are checked. Historical missing currency requires reconciliation; neither payment detail nor bill history infers it from current configuration or a UI dollar sign. The preview keeps background jobs, migrations and scheduled operations disabled. No production publication, financial posting, payment or payroll execution is authorized by this change.
