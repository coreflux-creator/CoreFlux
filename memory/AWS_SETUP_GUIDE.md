## Prepared infrastructure

Deploy in `us-east-1`, the existing Core default. The template creates:

- One private, versioned bucket with public access blocked and ACLs disabled.
- One rotating KMS key and an alias, in the same region as the bucket.
- A bucket policy requiring HTTPS, explicit KMS encryption, and this exact key ARN.
- Exact browser-origin CORS rules, initially `https://corefluxapp.com` and
  `https://www.corefluxapp.com`. Add the actual pilot origin if it differs.
- One **unattached** IAM policy for the corresponding Core server identity.
  It allows object reads/writes, tagging, and soft deletion within this bucket;
  encryption operations are limited to S3 and this bucket's encryption context.

Bucket names are generated by CloudFormation. Pilot and production must use
separate stacks, keys, identities, and credentials. The application identity has
platform-wide access within its environment's bucket; Core's server permissions
and tenant checks enforce isolation between tenants.

The bucket supports Object Lock, with no default retention period or legal hold.
Once enabled, Object Lock cannot be disabled and versioning cannot be suspended.
The runtime policy intentionally does not grant permanent version deletion,
retention changes, legal-hold changes, or governance bypass. Any future module
requiring those operations needs a reviewed policy extension.

Bucket, key, alias, and bucket policy are retained if the stack is deleted or
replaced. There is no automatic object/version expiration. Retained resources
continue to incur charges until separately retired. This template does not
configure antivirus scanning, MFA Delete, CloudTrail object events, backup
replication, or a legal retention policy; it is not evidence of those controls.

An account owner must complete AWS account registration, billing verification, and
MFA if there is no company AWS account. Use a company-controlled account and an
authorized administrator. Do not send passwords or secret keys in chat.

Before creating resources, review the current AWS pricing for S3 storage,
requests, transfer, and KMS key/request charges. Do not rely on the older guide's
free-tier or sub-dollar total estimate.

In CloudFormation, select `us-east-1`, upload the JSON template, name the stack
`coreflux-documents-pilot`, and use `Environment=pilot`. Review the five proposed
resources and IAM capability acknowledgment before creation. Turn on stack
termination protection. Record the stack ID and outputs without credentials.
When using a change set, verify termination protection after execution: the
console creation flow did not preserve the selected setting, so it was enabled
and verified separately after this pilot stack completed.

The template creates no IAM user, role, trust relationship, or access key and
attaches its policy to nobody. After provisioning, bind the output policy to a
dedicated server identity for this environment. Prefer a short-lived credential
mechanism already supported by the host. If Cloudways requires a programmatic IAM
user, create it without console access and give it only this policy; deliver its
key pair through the hosting secret configuration, not the repository or chat.
Never use account-root credentials.

## Core settings: configure the isolated pilot first

The stack outputs map directly to the existing driver:

| Setting | Value |
| --- | --- |
| `STORAGE_DRIVER` | `s3`, only after the file-location checks below |
| `STORAGE_S3_BUCKET` | `StorageBucket` output |
| `STORAGE_S3_REGION` | `StorageRegion` output |
| `STORAGE_S3_KMS_KEY_ID` | Full `StorageKMSKeyArn` output |
| `STORAGE_SIGNED_URL_DEFAULT_TTL` | `300` |

Use the full key ARN: the bucket policy rejects aliases, bare key IDs, missing
encryption headers, and another key. The existing server PUT and presigned POST
paths explicitly send the encryption fields; the default bucket setting alone
does not satisfy the policy.

With a static pair, use `STORAGE_S3_ACCESS_KEY_ID` and
`STORAGE_S3_SECRET_ACCESS_KEY` in the host's secret configuration. With the AWS
SDK default credential chain, leave both of those unset. Temporary credentials
must use the complete standard SDK configuration, including
`AWS_SESSION_TOKEN` and an actual refresh mechanism; Core's explicit
`STORAGE_S3_*` pair does not accept a session token.

Confirm the web PHP process sees the same settings as CLI before testing.
A successful configuration-presence check does not prove object access.

Keep Quanta document intake disabled until storage acceptance passes:
`COREFLUX_QUANTA_ONBOARDING_DOCUMENTS=0`. The existing allowlist
`COREFLUX_QUANTA_ONBOARDING_DOCUMENT_TENANTS` also limits the workspaces that may
import documents. No application settings are changed by deploying this stack.

## Existing-file compatibility before switching drivers

`STORAGE_DRIVER` selects one backend for the whole Core instance. Current
registry rows do not select a different backend per file. Switching to an empty
bucket can make existing locally stored documents unavailable.

1. Inventory `storage_objects`, legacy module file references, and actual
   local files for the exact target environment. A zero-row registry is not
   proof that no legacy files exist.
2. Record counts, canonical keys, sizes, and hashes. Preserve the source files
   and database backup. Resolve missing files and key collisions first.
3. Rehearse any migration in isolated staging. Copy files using the exact
   canonical keys and explicit KMS encryption, then verify hashes and downloads.
   People document intake uses `people/{owner_tenant}/document/{person_id}/...`.
4. Pause writes for the final inventory/copy and controlled backend switch.
   Validate existing module downloads as well as new uploads before resuming.

Do not switch production just to unblock one worker. After new files have been
written to S3, returning `STORAGE_DRIVER` to `local` alone is not a complete
rollback: those new files must remain available. Plan the reconciliation or
back-copy before any production change, and retain both copies.

## Pilot acceptance

Use synthetic documents and the actual staged application. Record results
without signed URLs, secrets, or worker-document content.

- Verify the target bucket, KMS key, versioning, public-access block, and exact
  browser origins using the deployed stack outputs.
- Exercise server upload, bounded byte read, and the browser presigned POST.
  Verify actual content, version ID, and KMS key. Repeat a reserved write and
  confirm the original bytes are not overwritten.
- Confirm an unsigned download, an HTTP request, and an upload using the wrong
  key are denied. Verify the short-lived signed download and its expiration.
- Test Core permissions: a different tenant and an unauthorized user cannot
  obtain or import the document. Bucket CORS is not an authorization boundary.
- Exercise Quanta import, receipt, retry, and missing-object recovery using a
  synthetic onboarding case; confirm replay does not duplicate its Core record.
- Verify soft deletion preserves an older version and that the runtime identity
  cannot permanently delete that version. Use an administrator for deliberate
  cleanup of synthetic evidence if required.

Only then enable document intake for the authorized pilot workspace and complete
its real document round trip. Retention and malware-scanning requirements remain
separate release prerequisites where applicable; do not claim a production
onboarding release from synthetic storage tests.
