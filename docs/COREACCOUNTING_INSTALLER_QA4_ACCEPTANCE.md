Date: 2026-10-09. This is an isolated, disposable Cloudways rehearsal, not a production release or a second home for any existing company's books. App `6718409` (`CoreAccounting Installer QA 4`) uses database `fyqqcqhwwr` on the existing server. It is a Custom App on the Hybrid stack with no paid add-ons. Production CoreFlux and populated CoreFlux staging were not changed.

## Hosted behavior

The app-scoped Cloudways site cache was purged. Its outside-in static-file audit checked 360 non-PHP paths: exactly 25 intended assets returned 200, 291 protected paths returned 403, and 44 absent paths returned 404. Unexpected serving, missing assets, byte mismatches, unexpected statuses and transport errors were empty. Direct requests to installer/bootstrap, simulation runner, core config, public vendor loader, unrelated People API and signup returned 404; the signed-out Reports API returned 401. A synthetic administrator signed in through the hosted login handler, and the signed-in income-statement API returned 200 with zero amounts for the empty first tenant.

Four accounting scenarios ran twice on the installed host: invoice, bill, AP payment and bank-feed categorization. First pass created five posted journals; second pass created none. The final synthetic snapshot reported AR `$2,500`, AP `$1,500`, assets `$1,525`, liabilities `$1,500`, equity `$25`, balanced income and balance sheet, and `$0` cash-flow/GL difference. All scenario assertions passed. The event layer still warned that `billing.invoice.sent` is a deprecated alias for `ar.invoice.issued`; this is a source migration to review, not a failed journal.

Later source commit `1076fa00` coordinates the canonical invoice emitter, posting rule, historical replay and legacy idempotency guard. Its fresh-database [CI run 37889700142](https://github.com/coreflux-creator/CoreFlux/actions/runs/37889700142) passed all eight jobs, but QA4 still runs the earlier installed package. The hosted result above is historical evidence, not verification of that later source on this host.

Cloudways support restored the provider-managed DNS record. On 2026-10-09, a fresh A-record lookup returned `138.197.121.111`, and the normal HTTPS hostname loaded a signed-in synthetic administrator session. The hosted overview, invoice creation, bill creation, banking worklist, bank reconciliation, reports index, income statement, balance sheet and cash-flow screens rendered without an observed error. The first tenant's statements correctly showed zero because it has no real opening balances or financial documents. This was a navigation and empty-state check, not an end-to-end customer workflow acceptance.

The bank-setup walkthrough found that the first-bank action led to a second Treasury form accepting a raw GL code, while the bank-account picker offered every asset account, including receivables and suspense. A source-only follow-up now routes Overview and Treasury to one bank-setup form, exposes cash-designated accounts in the picker, validates the ledger in both APIs, and lets operators mark an existing asset as Bank/cash. The local UI running against QA4's older backend completed one synthetic bank-account creation: account ID `2`, name `QA4 synthetic checking`, ledger `1000`, bank `Test Bank`, last four `0000`, entity `1`. It created no statement line or journal and connected no live feed. The resulting account-detail screen showed statement import and reconciliation actions. These source changes are **not installed on QA4**; the local UI/backend compatibility check does not prove the new server-side validation on that host.

The first installer version accepted a mail-log path whose parent was writable by the deployment user but not by the web PHP worker. After activation, a private empty log file was provisioned with mode `0660` and the app's `www-data` group. A synthetic password-recovery request returned the generic response and wrote one line through web PHP to that log; no external email was sent. Follow-up source commit `b83fc579` requires an existing empty private log file at installer preflight. [CI run 37888046087](https://github.com/coreflux-creator/CoreFlux/actions/runs/37888046087) passed all eight jobs, including the new guard and a fresh-database installation. That guard is not part of the hosted `9e89f4c9` runtime, and the exact hosted permission arrangement still needs to be checked on any future host.

## Remaining gates

The default hostname now resolves; [Cloudways support request 987550](https://tickets.cloudways.com/hc/en-us/requests/987550) records the provider repair. The newer source and installer/mail-log guards still need a controlled hosted upgrade and fresh verification. The bank-setup source check has not covered a second legal entity or the Plaid-created account path; current schema permits one bank account per tenant-level GL code, so multi-entity reuse of a standard code needs a design and migration decision. This QA test did not send customer mail, move money, run payroll, reconcile real opening balances, or obtain two independent human approvals. No production deployment or customer cutover is implied.
