# Placement document upload recovery

The previous reply answered standalone accounting access and made no integration change. This continuation revalidated the installed document release and successful eleven-job CI run 43226857316, then addressed the interrupted-upload gap found in the actual pilot browser.

The placement Documents screen now obtains its company, directory, placement, operator and upload permission from the authenticated document endpoint. A pending receipt is scoped to all four identities in tab session storage. It contains the original file reference, metadata and SHA-256 fingerprint, without signed credentials or file bytes. The receipt is persisted before the external upload, so an unreadable storage response or lost registration response remains recoverable after reload. The browser checks the original object and retries identical registration. An absent object can resume using the same key and the exact original file. The endpoint refuses a renewed upload URL for any existing object or any registered key, including retired or missing retained evidence.

The form prevents simultaneous submissions, stops follow-up writes after a workspace or placement change, rechecks write permission after the storage transfer, and retains a confirmed registration receipt without relying on a subsequent list refresh. Read-only users have document viewing controls without an upload form. The file transfer has a bounded timeout. Download requests explicitly bind the displayed placement.

Release review also found that the S3 adapter previously returned the same null result for missing files, access denials and transport failures. Only an SDK response with HTTP 404 now means absent; other errors propagate to the module's unavailable-storage response. The real installed SDK package test exercises successful metadata, 404, 403, 500 and a transport exception through an intercepted handler, following the [AWS SDK handler testing interface](https://docs.aws.amazon.com/sdk-for-php/v3/developer-guide/guide_handlers-and-middleware.html). It performs no cloud calls.

Twelve component scenarios exercise lost registration replies, reload recovery, unreadable storage replies after actual arrival, same-file resumption, read-only access, permission and company changes during upload, directory changes, duplicate submits, unmounts, browser storage refusal and unconfirmed registration replies. All 350 dashboard component tests pass, the production bundle builds, and 27 document validation checks plus the upload-bridge checks pass locally. Native cookie/database checks have been extended for context, same-key renewal, upload status, overwrite refusal and placement-bound downloads; their release CI and hosted acceptance are recorded separately when complete.

This does not complete the wider integration. Full browser upload acceptance still requires the pilot origin to be allowed by the existing private S3 bucket.
