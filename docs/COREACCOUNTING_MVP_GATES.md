# CoreAccounting MVP release gates

CoreAccounting is an independent product surface on the **existing CoreFlux/CoreOne accounting core**. Invoices, bills, bank transactions, approvals, subledger links and posted journals remain in their current source modules and shared ledger. This checklist is an acceptance ledger, not a claim of production readiness. Detailed evidence and decisions live in `COREACCOUNTING_COREONE_ALIGNMENT.md`. The fresh-package hosted check and subsequent private-runtime package update are recorded in `COREACCOUNTING_PACKAGE_QA3_ACCEPTANCE.md`.

For each behavioral release, create a representative synthetic item in isolated QA, verify its persisted outcome through the user workflow and source audit where applicable, and run the complete CI suite on the final commit. Record the test item, result and run link here; preview-only checks do not satisfy this gate. Never use production data for this requirement.

## Decision register

- **Deployment boundary:** Cloudways does not permit this deployment account to create or rename a sibling release directory beside its assigned `public_html`, so the current host cannot truthfully offer an atomic directory swap. The clean-app CLI verifies a trusted release and empty database, fingerprints and backs up the target, copies private/public files, restores the webroot on a post-copy failure, and forces log-only mail. QA4 later exercised a separate populated-app code-only path: it required exact old/new release manifests, matching live files and zero migration differences; refused a wrong fingerprint; retained both previous runtime trees; and verified the newly copied code. Neither path runs host-specific cache purge and acceptance inside one atomic transaction. A schema-changing upgrade needs a separate migration and rollback design; file restoration cannot roll back database changes. Hosted operational cutover remains open.

- One authoritative ledger and one set of source-owned financial documents per organization; standalone does not mean a second copy of that organization's accounting data. The additional Cloudways app/database is a disposable clean-install test with invented data, not a destination for current customer books. A future standalone organization's own database could serve CoreOne through scoped service APIs, but those cross-app contracts remain an explicit integration gate. Existing organizations stay on their canonical CoreFlux/CoreOne database without an approved cutover.
- Bank setup should use one Accounting form from Overview, Treasury and reconciliation. A bank account must map to an active, postable cash asset: the seeded system Cash account or a custom chart account explicitly tagged Bank/cash. Other seeded system assets cannot be retagged into bank ledgers. A receivable, clearing or suspense asset must not be selectable merely because it has a debit balance. **Decision:** preserve one cash GL ledger per physical bank account for the MVP so a bank line can be reconciled to a specific journal movement. Plaid Link and orphan recovery now allocate distinct ledgers, and the former shared-GL toggle is removed. The current tenant-level unique bank/GL key still prevents two entities from reusing the same chart code; simply relaxing it would duplicate or misattribute cash in joins that still key by tenant and code. The broader multi-entity index and grouped-chart design still need a coordinated migration and second-entity acceptance before release.
- A linked bank, card or loan must retain its reviewed legal entity on reconnect. Do not silently fill a legacy null owner or adopt one of several same-institution/last-four candidates; route those records to explicit accounting ownership repair and review. Recovery must require an explicit account selection, including when an operator previously opted out of mirroring an account. These rules are source-tested; no live Plaid connection has been accepted yet.
- Standalone Billing's invoice form depends on the shared company directory for client lookup and creation. The exact `modules/people/api/companies.php` script is therefore allowed through the standalone Apache, server-path and API-bootstrap guards, while the broader People module remains denied. The hosted QA client-create action returned 201 and a new custom-line invoice draft returned 201; signed-out directory access returns 401, not a public listing.

The login illustration was later removed because it pushed the form below the first viewport. The existing form, handler and deep-link behavior are unchanged; its legacy marketing links were removed because those pages are not part of standalone CoreAccounting. QA browser review shows the complete form at desktop and 390px mobile widths with blue trim. Standalone does not link the ERP-only PWA manifest; a purpose-built CoreAccounting manifest and installability check remain open.
