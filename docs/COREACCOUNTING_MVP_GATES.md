## Decision register

- One authoritative ledger and one set of source-owned financial documents per organization; standalone does not mean a second copy of that organization's accounting data. The additional Cloudways app/database is a disposable clean-install test with invented data, not a destination for current customer books. A future standalone organization's own database could serve CoreOne through scoped service APIs, but those cross-app contracts remain an explicit integration gate. Existing organizations stay on their canonical CoreFlux/CoreOne database without an approved cutover.
- Standalone Billing's invoice form depends on the shared company directory for client lookup and creation. The exact `modules/people/api/companies.php` script is therefore allowed through the standalone Apache, server-path and API-bootstrap guards, while the broader People module remains denied. The hosted QA client-create action returned 201 and a new custom-line invoice draft returned 201; signed-out directory access returns 401, not a public listing.
- The lean QA package uses existing `/assets/brand` images for the shared sign-in page; the former icon paths were absent in that package. The login illustration was later removed because it pushed the form below the first viewport. The existing form, handler and deep-link behavior are unchanged; its legacy marketing links were removed because those pages are not part of standalone CoreAccounting. QA browser review shows the complete form at desktop and 390px mobile widths with blue trim. Standalone does not link the ERP-only PWA manifest; a purpose-built CoreAccounting manifest and installability check remain open.
- Retained legal/QBO compliance pages and the old 404 HTML had also referenced the omitted `/assets/icons` tree. They now use shipped brand images; the 404 action goes to `/`, not the retired `/index.html`, and its layout was visually checked on disposable QA. The legal text and integration links were not changed or accepted by this visual check.
- CoreAccounting admits the accounting, Billing, AP and Treasury module APIs and four bearer-scoped CoreOne v1 finance contracts. The server-resolved entry-script classifier rejects known unrelated flat APIs and root PHP pages before private database config loads; the CoreFlux ERP retains its existing routes. Direct scripts that never load common config still need webroot packaging or server-level routing. The flat, nested, module and root PHP path inventories have been checked on QA, but static paths and database-backed behavior remain open. Missing `.php` files must return 404 before the SPA rewrite; two Treasury wrappers with missing dependencies were retired rather than presented as working endpoints. The finance editors do not offer staffing-only dimensions in standalone mode. A journal already linked to a placement remains readable but cannot be changed there because its assignment context requires CoreFlux verification.
- A standalone release must publish only the active SPA entry and its referenced chunks; old hashed bundles and alternate static shells are not runtime dependencies. The disposable QA finalizer validates that entry before moving files, retains required legal/QBO pages, and privatizes unexpected root files, old bundles, the legacy data directory, dist bundle copies, and observed non-finance module trees. QA moved 53 root/static entries and then three legacy module directories. After observing that Varnish still served two removed files, 57 then 105 QA-host paths were purged. Representative old static and module URLs now return 404; current assets and finance navigation remain available. The retired `/data` namespace and unrelated module namespaces have standalone-only Apache 404 rules, with an exact shared company-directory exception. A full nested static-file inventory and automatic app-scoped cache invalidation remain release gates.
- The broken legacy public signup is not part of CoreAccounting and is retired from the shared source as well. The existing login remains the sign-in surface; new access is granted by a workspace administrator. Password reset stays public but must use `core/db.php` and the configured `APP_URL`, never the old direct database file or an untrusted request Host header. Read-only reset-page loads must not repair schema. A database-backed reset email and redemption test is still required before release.
- An entity-bound service key may prepare documents and request review only under its explicit scopes; a human reviewer owns approval and posting.
- The AP payment creator cannot release their own draft or queued payment. The shared UI explains this and excludes creator-owned payments from bulk release and draft bank-batch origination; the server remains authoritative. A cleared payment is corrected by a reasoned reversal, not by deleting its posted journal. The source bill reopens and the bank line must be matched again to a replacement payment. This preserves the audit chain across correction and recovery.
- A hard accounting close is allowed only after that period's end date and after every earlier period for the same legal entity is closed or locked. Both checks run under the same entity/period lock as posting and cannot be bypassed by marking checklist tasks complete. An operator may prepare the checklist or soft-close earlier; the month-end screen explains why hard close is unavailable. The existing database-clock `ready_to_close` filter and the new `has_ended` field use the same boundary. This avoids prematurely freezing a current month or letting an earlier open month change balances behind a later close.
- Generated finance PDFs must use a private, per-request temporary directory, not a fixed shared folder that another server user may own. The close packet, money-movement digest and AR statement now share that response helper, which cleans temporary files and keeps renderer paths out of customer-facing errors. Clean QA verified saved close-packet HTML/PDF integrity and a digest PDF after the fix. It also posted an invented $7.77 open receivable through two synthetic identities and downloaded an entity-scoped statement PDF whose current and total-due amounts both read $7.77. Saved packets are immutable, so the earlier rendering defect remains visible in packet 1 while packet 2 carries the corrected date and reopen wording.
- Manual AP discounts are refused until a credit-side treatment, tax behavior, source correction and report tests are defined. A positive `discount` label must never silently debit expense.
- The AP editor must not offer a discount as a new bill-line choice while the backend refuses it. If a PDF extraction surfaces a discount, preserve it visibly but block save with a vendor-credit explanation. Blank untouched rows may be skipped; a partly completed row must not disappear from a saved bill.
- Direct invoice drafts use the canonical Billing service for both standalone CoreAccounting and CoreOne. Untyped negative lines become untaxed discounts; an explicitly typed discount must be negative and non-taxable. Zero-priced informational service lines are allowed alongside a positive invoice, but zero- or negative-net documents cannot be saved or edited into that state. Blank untouched form rows may be skipped; a partly completed row must be corrected or removed. Browser previews round each line before summing, matching the backend calculation.
- An AP bill CSV line must carry positive quantity and unit price at no more than four decimal places. For an amount-only vendor charge, use quantity `1` and the charge as unit price; subtotal and total are derived or checked in preview. One invalid line blocks the entire bill, including when other bills are imported with `skip_invalid`.
- Invoice CSV uses its own signed-line rules: positive quantity and an explicit rate at stored four-decimal precision; explicit subtotal, tax and total amounts must use cents; subtotal must match quantity times rate. An untaxed negative discount line is allowed only within a net-positive invoice. These checks apply to preview and commit and cannot turn one partially invalid invoice into a saved draft.
- Imported invoice CSV lines accept an explicit supported item type; otherwise a negative subtotal becomes `discount` and a nonnegative manual line becomes `other`. A negative line cannot be mislabeled as labor or another positive type. An optional catalog item ID must resolve to an active item in the same workspace; its type and revenue account are inherited when omitted from the line. An explicit or inherited revenue account must be active, postable and revenue-classified. CSV invoices now resolve an existing client-company ID or upsert by name through the same Billing helper as direct invoices; preview does not create a company. Ordinary line-level CSV export carries the stored customer, item, type and account identities. Synthetic source-to-collection passed; real bank, delivery and historical acceptance remain open.
- Synthetic staging tests are useful engineering evidence but do not replace real-history reconciliation or human operational acceptance.
- Migration identity is based on SQL content with normalized LF line endings. The shared runner and first-tenant guard recognize both new canonical hashes and legacy LF/CRLF file hashes, so a Windows-built archive alone cannot replay an unchanged migration. Failed sentinel hashes and genuinely changed SQL still demand a retry. The three new Billing migrations are pinned to LF in Git; local migration-hash checks passed 9/9, and existing splitter, retry, cursor-drain, installer and update checks passed. A read-only hosted QA audit now confirms all 281 installed canonical migrations match their database ledger records, with zero pending, changed, failed or unpackaged rows. This does not prove a populated ERP's in-place release migration.

The QA override must be removed before a real-provider or live release.

A successful resend rotates earlier links and preserves paid/partially paid status. An ambiguous provider result retains the possibly delivered link and requires an audited human decision before another send; declaring non-acceptance revokes only that attempt's link. The shared Billing GET returns link and delivery state, never the raw secret; MailService redacts the URL from its persisted outbox body while sending the original message. The LogDriver records metadata but not bodies. Migrations 022-023 require a coordinated release on a populated ERP, since old Billing code reads the removed column and new code requires the new columns.
