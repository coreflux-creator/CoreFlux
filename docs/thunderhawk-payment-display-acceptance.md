# Isolated provider payment-display acceptance

On November 12, 2026, the isolated Thunderhawk provider received the coordinated payment-display correction. The public PurePay deployment, Core runtime, Quanta and Arabella were unchanged. This addresses the read-time invoice-label writes found during the native staffing round trip; it does not complete the full integration.

The application change is `a69981c912e97a8ba8d5a9bbce54b10756ee57cd`, ported as `e54f50a68e6e5dc3b2593639b2b01e9e8c06522f`. Only `_enrich_payments` changed in the installed `server.py`. The helper rejects missing/mixed company identities, scopes bill and vendor lookups to that company, copies caller-owned records, and derives display labels and cached provider references in memory. It no longer writes enrichment back to payment rows or makes the Mercury lookup. Seventy-six behavior/regression cases passed, including eighteen enrichment cases. The reviewed `release_handover.json` accompanies the source change.

## Release correction and verification

The first two installations restored the prior version after readiness failed. The second established an actual application exit. Read-only diagnosis reproduced a source/stamp mismatch: the original stamp described digest `9b381221dadacd65b68c1d5056abd0dcd5c4bb41fd07660c297b80a2e1baa058`, while the new helper produced `34019fb08c3fe17541c401f67576e03727ed8969d6102bbc6d0c9373b6507624`. The isolation gate correctly refused that mismatched package. Candidate logs were not retained by those initial rollbacks, so the diagnosis is an independent gate reproduction rather than a recovered traceback.

The installer now validates the exact source/stamp pair before mutation and before restart, preserves both prior files, and captures failed-container logs privately before any rollback. Five automated release-contract tests cover stale stamps, exact reviewed pairs, other runtime drift, line-ending/exclusion rules and invalid stamp identity. They run in Core CI. The installed `PilotGate` was separately exercised against a temporary candidate tree: it rejected the old stamp, accepted the reviewed pair and continued to refuse production activation. That check made no database calls or service restart.

The corrected installation completed at **22:32:29 UTC**. All 310 provider source fingerprints were checked. All 119 then-current records across 26 collections, indexes, service configuration and 208 other containers were preserved. The running service remains in isolated-pilot mode with background jobs, startup migrations, scheduled operations and provider egress disabled. Payment/payroll execution and production activation routes still refuse requests. The installed source/stamp hashes and full evidence are in [the manifest](../deploy/thunderhawk-payment-display-20261112.json).

The installed helper passed five checks against the actual pilot database: missing cached labels were projected in memory, repeated projection preserved caller inputs and saved payments, amounts/status/IDs stayed unchanged, foreign-company input was rejected, and provider lookup was not invoked. Native detail routes then loaded both terminal payments twice, and the existing held payroll draft remained recoverable. All 83 business rows across 24 non-authentication collections remained unchanged; only ordinary test authentication metadata was excluded. The verification session was revoked.
