# Person profile ownership and private input

The native person-field review found two real write-boundary gaps. The generic PATCH endpoint accepted arbitrary table columns, including internal account association, financial routing and document-object references. The read path treated gender and marital status as private, but create/update did not include them in the private-write permission list. These findings came from the actual endpoint, profile UI, employment helper and private-read field list, not from column-name inference.

The installed change adds an explicit native profile input list shared by create and update. Unknown/internal fields are rejected before a partial update can occur. All read-private profile fields use the same private-write list, including explicit clears. Valid profile edits, reviewed employment-type/hire-date handling and existing provider identity mappings remain separate. This change does not establish legal-employer validation, lifecycle propagation, automatic provider reactivation, or a replacement worker-routing editor.

The field dictionary defines native person meanings and owners, marks personal addresses/demographics and internal notes as restricted, and retains existing JobDiva/Quanta/PurePayroll adapter evidence. Secondary contact and separate middle/preferred-name transport remain explicit receiver gaps. Work authorization, directory classification, payroll cadence and legacy routing are not silently converted into provider employment or login authority. Unknown future fields remain unreviewed.

Local checks pass: 301 profile-input/field-contract assertions, 111 existing ownership assertions, 643 commercial field assertions, 371 record-number assertions, 81 extended-field assertions and PHP syntax checks. The expanded native HTTP fixture passed 362 checks through real login, session and API paths, including read/write roles for demographics and explicit clears, rejection of account/routing/storage/internal fields without partial application, preserved ordinary profile editing, authorized private updates and foreign-company refusal. Its temporary actor, connection and session files were retired.

The first expanded run [43342105885](https://github.com/coreflux-creator/CoreFlux/actions/runs/43342105885) failed two lanes. Two older smoke assertions needed to follow the reviewed external-reference rule and shared private-field list. More importantly, the actual authorized private-edit request exposed a legacy schema mismatch: the original private-access table records employees, while the newer helper attempted to insert person identifiers into a different set of columns. The correction writes required, person-qualified receipts to the existing platform audit table and presents original employee/person history without rekeying it. Receipts contain field names, not private values. A read-only hosted schema inspection also showed that request identity belongs in supported audit metadata rather than a nonexistent column; the final implementation retains both request identity and user-agent context. Native private creates and mixed profile/employment edits roll back when their receipt fails; private reads release no record if logging fails. The expanded HTTP checks cover successful reads and writes, legacy numeric-ID collisions, permission/company boundaries and induced audit failures.
