The generic Time API now saves and corrects time through the same protected directory transaction as native staffing edits. Entries, weekly headers, periods, custom categories and uploaded documents retain their originating workspace even when people, placement, staffing or time directories are shared. The existing self/manager permission decision remains with the authenticated caller. New and moved work revalidates the current worker and unmerged placement, the actual placement dates, original and target open periods, and the daily 24-hour limit. Precision that would become zero stored hours is refused.

Moving an editable entry to a different week updates both weekly totals and artifacts in the transaction. It retains the source reference, synchronizes hour type and billable/payable metadata, permits explicitly clearing a custom category and returns the edited row to draft. It cannot alter an approved, superseded, extracted or Quanta-sourced row. Quanta source flags still protect a row if its import relationship is absent.

Uploaded rows and document consumption commit together. A late validation or required-audit failure rolls back all rows, headers, periods, artifacts and source consumption. The existing single-row source-ref contract consumes the source document through the same transaction; retrying it cannot bypass the bulk upload's duplicate guard. A batch must reference one original-workspace document consistently.

Manual approved-time correction requires a reason, retains the original entry's date, hours, source, rate and approval evidence, marks it superseded and creates a linked draft replacement on the appropriate weekly header. It recomputes the original and target weeks while retaining approved siblings. A repeated or competing correction cannot replace the same original twice. Closed periods, downstream use, Quanta source revisions and retired placement identities require their appropriate review workflows; ordinary correction cannot silently retarget them. Required before/after audit evidence is part of the transaction.

The weekly detail screen now evaluates each row's editability. Approved/imported/downstream/locked/retired rows remain read-only within an otherwise editable week. If refreshed data makes a row read-only, stale local edits no longer appear in totals, highlights or save-all controls. The authoritative server checks still apply.

## Remaining acceptance

The new fixtures exercise the real generic API with a native signed-in session, grant changes, original-workspace isolation, cross-week moves, uploaded batches, correction history and injected late audit failures. Independent connections cover committed and rolled-back approval, supersession, Quanta binding, archive, merge, person archive, period locking, daily capacity and directory changes, plus competing corrections and document consumption. Their exact final run and temporary-access cleanup are recorded in the pinned evidence above.

Time catalog/setup consumers also require alignment before the full pilot upgrade. `modules/time/api/categories.php` still uses request-effective scope for category management, while these new entry writes validate a category in the original workspace. Period setup/listing, CSV imports and custom-category bucket/overtime metadata need an end-to-end review with the entry services; passing entry tests alone does not establish those operator paths. In particular, the existing `timeCategoryRowMeta` treats custom categories as nonbillable and does not consult their configured bucket.

This increment is not installed on the pilot. Submission/rejection/approval services still need their remaining ownership, concurrency, required-audit and frozen-dimension work, including weekly and tokenized entrypoints. The existing generic correction endpoint has no caller in the Time or Staffing React screens: an explicit review-and-create-replacement UI, with original/replacement history, still needs implementation and rendered/native acceptance. Read-only row controls alone do not complete that operator workflow. Generic placement CSV, native job ownership, AP/current references, stable outbound QuickBooks customer identity and the complete field/portal/document/payroll/result/reconciliation round trip remain open. The guarded pilot upgrade and signed-in hosted acceptance must use the full reviewed release and required migrations. Production and the separate Arabella accounting pilot are unchanged; this increment runs no real provider, payroll, payment or financial posting.
