# CoreAccounting on the CoreFlux accounting core

## Decision

CoreAccounting is a workflow surface over the existing CoreFlux ERP accounting engine. It must not maintain a second ledger, invoice balance, bank reconciliation, or financial database. The local SQLite interaction prototype remains on a separate branch and is not part of this implementation or a production migration path.

| Concern | Canonical owner |
| --- | --- |
| Authentication, tenant and permissions | `core/api_bootstrap.php`, tenant context and module RBAC |
| Journal posting, reversal, periods and dimensions | `modules/accounting/lib/accounting.php` and `core/posting_engine/process.php` |
| Invoices, payments and AR | `modules/billing` |
| Bills, payments and AP | `modules/ap` |
| Bank feed and reconciliation | `modules/accounting/api/bank_statements.php` and `reconciliations.php` |
| Financial statements and aging | `modules/accounting/api/reports.php` and `standard_reports.php` |

## First slice: invoice to cash

- Accounting navigation leads to the native invoice workflow. A completed invoice approval posts through the existing Billing endpoint; a configured policy still controls approval.
- Sending requires a posted journal entry in the API, not just in the UI. Posting an invoice that already links to a posted journal returns that entry on retry.
- The invoice shows its journal link and tenant-scoped unmatched deposits from compatible bank accounts. A user explicitly applies an exact receipt, a smaller partial receipt, or opens the bank split screen for larger and multi-invoice deposits.
- For both direct and split receipts, the cash journal, Billing payment allocation, and bank-line match commit as one transaction. Pay-when-paid release runs after commit.
- No CoreAccounting-specific financial table or parallel balance calculation was added.

## Gate before live use or CoreOne packaging

Run the full flow against an isolated MySQL ERP tenant: draft, approval policy, journal posting, sending, exact and partial receipts, split across invoices, retry, failed-allocation rollback, reversal, tenant/entity isolation, and agreement among AR aging, GL, trial balance, cash flow and bank reconciliation. The isolated staging and local MariaDB checks below cover substantial portions of this gate, but do not constitute production-history or operational-release acceptance.

AP and the CoreOne-facing document and journal contracts are being built on those same modules. The remaining gate is end-to-end operational acceptance across their source workflows, not a separate ledger build. Deployment may be separate; ledger authority may not.

## Connecting the local UI to the canonical backend

The Vite dashboard is only a frontend. Its development server forwards `/api/*`, `/core/api/*`, `/modules/{module}/api/*`, the existing `/login.html` page, session/login/logout/tenant-switch requests, and static `/assets/*` to the CoreFlux PHP backend. Ordinary `/modules/*` screens remain in the local SPA. The browser never connects to MySQL directly. There is no CoreAccounting-specific sign-in or identity store.

For an isolated hosted staging installation, set `COREFLUX_BACKEND_ORIGIN=https://<staging-host>` in `dashboard/.env.local`, then run `npm run dev` from `dashboard`. Leave `VITE_API_BASE` unset so all requests use the same-origin proxy and session cookie. The proxy strips the upstream cookie domain for local development and rejects CoreFlux production/tenant domains unless `COREFLUX_ALLOW_PRODUCTION_PROXY=1` is explicitly set. The default backend remains `http://127.0.0.1:8080` when no origin is configured.

Staging must have its own PHP deployment, MySQL database, migrations, encryption key and test tenant. Verify login and invoice-to-cash against that staging tenant before making the CoreAccounting UI available for operational use.

## Receipt correction pass (October 2026)

- A matched bank receipt now has a **Correct receipt** action with a required reason. The action reverses the cash/AR journal, marks its invoice allocations reversed, voids the source payment records, restores invoice balances, and reopens the bank line in one database transaction. It retains the original records, links the reversal journal, and shows the number of corrections on the bank line. It does not transmit or refund cash.
- The action refuses a receipt in a closed bank reconciliation or one whose invoice has already released a pay-when-paid vendor bill. These situations need the reconciliation or downstream AP consequence handled first. It also refuses inconsistent receipt/payment/allocation amounts rather than guessing a correction. Generic journal reversal and unmatch remain unavailable for a source-owned receipt.
- Each correction increments the bank line's durable receipt attempt. A later match uses a new posting idempotency key and payment external ID, so it cannot revive a reversed journal or voided payment. Current invoice detail, bank matches, dunning, delivery lifecycle and cash-cycle views exclude reversed allocations; AR aging uses the reversal timestamp to preserve historical as-of results. Payment exports include correction date, reason, and reversal journal.

## Manual and imported customer receipts (October 2026)

- Billing's **Record payment** now requires a receiving bank account and full allocation to posted invoices for the same client, currency and legal entity. The payment, invoice allocation(s), and balanced cash/AR journal commit together through the ERP's canonical posting service. A failed allocation or posting leaves no new payment. The operator can apply oldest-first or choose invoice amounts; partial settlement of an invoice is supported. Unapplied overpayments are not silently booked as AR: use bank receipt splitting until a customer-deposits liability flow is modeled.
- A request key makes a repeated manual submission return the original payment and journal. A bank statement line imported later can suggest and match that posted journal; it does not create a second Billing payment or cash entry. The receipt list distinguishes pending, posted, and corrected records and links to the journal.
- CSV-imported manual payments remain **Pending ledger** until an operator chooses the bank and posts the full allocation. The old standalone `allocate` endpoint now refuses to mark an invoice paid without posting cash and AR. Receipts imported under a non-manual source system are not posted by this manual action; their source integration needs its own posting contract. The weekly money-movement cash-in total excludes pending and corrected rows. Receipt CSV exports now carry the posting state, bank account, original journal and reversal journal IDs so a downloaded row can be traced back to the books.

A bank-reconciliation-created payment is marked posted in the list and explicitly refused by the manual posting service; otherwise it could create a second cash entry for the same deposit.
- Manual receipt correction requires a reason and reverses the canonical journal, allocations, invoice paid/due status, and any bank-line match in one transaction. It refuses a closed reconciliation, a released pay-when-paid bill, or inconsistent amounts. This is not a cash refund.

## Customer deposits and recorded refunds (October 2026)

- This section supersedes the earlier **no unapplied cash** limitation for manual receipts. An operator can explicitly hold a full receipt or a remainder as a customer deposit. The original journal debits the selected bank and credits system liability `2300` for the held amount; any contemporaneous invoice allocation credits AR `1100` separately. An existing tenant with a conflicting custom `2300` account is rejected rather than silently posted to the wrong liability.
- A later application to a posted invoice of the same client, currency and legal entity debits `2300`, credits `1100`, updates the shared Billing allocation and invoice balance, and retains its own journal and request key. It cannot precede the receipt date, exceed the held balance, or apply to another client. A corrected application reverses that journal, allocation and invoice paid/due state atomically. Pay-when-paid releases block correction until their downstream bills are handled.
- **Record refund** is an accounting action for money already returned to a customer, not a transfer instruction. It debits `2300`, credits the chosen active bank GL, lowers the available deposit, and keeps a separate refund record and journal. A CSV bank outflow can match that journal without creating a second posting. Correcting an erroneous refund record reverses its journal, restores the deposit balance and reopens a matched bank line; a closed bank reconciliation blocks correction. A real payment returned to the company must be recorded as a new receipt, not treated as a correction.
- The Billing payment list shows held balance, refunded amount, application/refund history, and links to original and reversal journals. Neither an application nor a refund is erased. Generic JE reversal remains unavailable for source-owned entries. A read-only deposit audit compares original liability credits to active applications, active refunds and remaining balances, and verifies every source journal link.
- New manual receipts store a fingerprint of bank, client, date, amount, method, currency, reference, notes, allocation instructions, and deposit choice. An exact request-key retry returns the original receipt; a changed intent is refused. Older receipts without a fingerprint cannot be replayed through that key and must be reviewed instead of presumed identical.
- New direct receipt and deposit-application allocations use their business posting date in Billing's shared allocation record, so backdated entries appear in historical AR aging on the correct date. Older allocations are not silently rewritten; historical data needs a separate reviewed audit.

## Reviewed processor payout to bank (October 2026)

- A captured QuickBooks Payments receipt stays in GL `1010` clearing until an operator selects one or more eligible captures against an incoming CSV bank line. The service checks the posted Billing receipt, charge shadow, tenant, legal entity, currency, capture date and available clearing balance. Selected gross captures minus the explicitly reviewed fee must equal the net deposit to the cent. The journal debits the bank's cash GL for net, debits a chosen active expense account for fees, and credits `1010` for gross. The bank match and source links commit with the journal. This is a CoreFlux Billing/accounting workflow on the existing ERP ledger, not a second CoreAccounting book.
- A bank line with an existing match or posted source journal/link cannot create a second cash entry. An exact retry returns the original payout; a changed retry is refused. Generic bank unmatch is blocked for these source-owned journals. **Correct payout** requires a reason, reverses only the payout and fee journal, and reopens the bank line. It deliberately leaves the captured customer payment and invoice application intact for a reviewed replacement payout.
